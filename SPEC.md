# seo-agent — Specification

A Claude Code plugin that runs SEO for any StaticMaker product. Installed into a product repo, it bootstraps itself, then runs on a schedule: reads search data, decides what to do, writes or refreshes articles (with images), opens PRs, reviews its own work, and learns from what gets merged or rejected.

Status: spec, pre-build. First test product: **RecordMover**.

---

## 1. Principles

1. **No server.** Everything lives in two places: this plugin repo and the product repo. Data snapshots are JSON files committed to the product repo. Git is the database.
2. **No extra API spend.** Reasoning runs on Claude Code under the owner's subscription. Search data comes from Google Search Console (free) and DataForSEO (already paid). Images are rendered from brand-driven HTML templates — no image-generation API, no browser automation.
3. **Skills, not framework.** The agent is Claude Code + markdown skills + a few deterministic scripts. No custom agent loop, no orchestration code.
4. **State is files.** Every run starts cold. All memory is in `/seo/*.md` in the product repo, versioned with the content it acts on.
5. **Output is PRs.** Nothing publishes without a pull request. The owner merges by hand until trust is earned, then an auto-merge dial opens per PR type.
6. **One agent, many products.** The plugin is product-agnostic. Everything product-specific is in the product repo's `/seo/` folder and `CLAUDE.md`.
7. **Idempotent runs.** Any skill run twice on the same day must not produce duplicate work. Each skill checks existing state (`backlog.md`, open PRs) before acting.
8. **Self-onboarding.** `init` does the discovery; the owner only does what needs their login or judgement.

## 2. Architecture

```
GSC API ──┐
DataForSEO MCP ──┤  read at run time, snapshots committed to /seo/data/
GEO monitor ──┘
        │
        ▼
Claude Code scheduled run, product repo checked out, plugin loaded
  reads  /seo/*.md, /seo/data/, articles
  writes branch + PR, /seo/backlog.md, /seo/done.md, /seo/data/
        │
        ▼
GitHub PR  ──►  seo-agent:review (fresh session)  ──►  owner merges / closes
        │
        ▼
Dashboard artifact (agent writes rows at end of each run)
```

Runtime: claude.ai **scheduled tasks** with the product repo attached (each firing is a fresh session). Fallback: cron on a server with `claude -p`. Local development: `claude --plugin-dir ../seo-agent` inside the product repo.

## 5. File contracts

### `CLAUDE.md` (product) — section the skills depend on

```
## SEO agent
- Articles: <path glob>, format: markdown with frontmatter
- Frontmatter schema: title, slug, description, date, updated, cluster, target_keyword, image, draft
- Images: <path>/<slug>/
- Validate: <command>
- Preview: <command or URL pattern>, optional
- PR label: seo
- Human-edited guard: 14 days
```

### `strategy.md`

```
# Strategy — <product>
## ICP
## Positioning (one paragraph)
## Clusters            (hub + spokes, target keyword each, priority 1–3)
## Competitors         (domains for gap analysis)
## Never write about   (hard exclusions, enforced at scoring)
## Caps                 new_per_week: 1, refresh_per_week: 2, open_prs_max: 3
## Auto-merge           [] | [refresh] | [refresh, write]
## Tracked keywords    (list; analysis may propose additions via PR)
```

### `backlog.md` — one item

```
### [B-042] refresh: /blog/zoom-recording-storage-limits
- type: refresh | write | fix | link
- score: 8.1  (potential 9 × ease 8 × fit 9, normalised)
- evidence: "zoom cloud storage limit" pos 11, 420 imp/28d, CTR 1.2%
- action: add section on 2026 plan limits, FAQ, 3 internal links
- status: open | claimed:<date> | in-review:<pr#> | done | dropped:<reason>
```

### `done.md` — one line per merged item

```
- 2026-11-03 B-042 refresh /blog/... pr#118 | outcome 2026-12-01: pos 11→6, clicks +38%
```

### `rejected.md`

```
- 2026-11-05 B-044 write /blog/... pr#120 | "too generic, reads like every other listicle"
```

Three rejections with the same theme → `feedback` proposes a line in `voice.md` or `review-rubric.md` via PR.

### `brand.json`

```json
{ "product": "RecordMover", "domain": "recordmover.com",
  "colors": { "primary": "#...", "accent": "#...", "bg": "#...", "surface": "#...", "text": "#...", "muted": "#..." },
  "fonts": { "heading": "Inter", "body": "Inter", "source": "google|local" },
  "radius": "12px", "logo": "public/logo.svg", "motif": "dots|grid|waves|none",
  "derived_from": ["tailwind.config.js", "resources/views/layouts/app.blade.php"] }
```

## 6. Scripts

| Script | Input | Output | Notes |
|---|---|---|---|
| `gsc.js` | `--site`, `--from`, `--to`, `--dims query,page` | JSON rows: clicks, impressions, ctr, position | Service-account JSON from `GSC_SA_JSON` env. Data lags ~3 days; always query `today-3` back. |
| `render.js` | `--frame <name>`, `--data data.json`, `--out file.png`, `--scale 2` | PNG (and WebP) | Fills a frame template from `/seo/frames/` with data + `brand.json`, renders with headless Chromium. Local files only, no site access. |
| `validate-article.js` | `--file` | exit 0/1 + report | Frontmatter schema, internal links resolve, images exist, word count within range from `strategy.md`. |
| `dashboard.js` | `--product`, `--event`, JSON payload | — | Writes a row to the dashboard artifact DB. |

All scripts print JSON to stdout so skills parse them with Bash.

## 7. Skills

Every skill:
- starts by reading `/seo/strategy.md`; exits with a clear message if missing ("run /seo-agent:init")
- never asks the owner a question mid-run; decides, logs, moves on
- ends by calling `dashboard.js` with a run summary
- never deletes an article; consolidation = redirect + PR explaining why
- never touches an article a human edited in the last 14 days (`git log` check)

### `init` — bootstrap a product
Trigger: owner, once per product (re-runnable: diffs and reports, never overwrites owner-edited files).
1. Detect article storage: routes, markdown folders, existing posts → write the `## SEO agent` block into `CLAUDE.md`
2. Read all articles + live site → draft `strategy.md` (clusters, ICP, competitors found in content) and `voice.md` (from existing writing)
3. Run `brand` → `brand.json` + design-system block; then `frames` → `/seo/frames/`, contact sheet
4. Create empty `backlog.md`, `done.md`, `rejected.md`, `review-rubric.md`, `data/`
5. Create `seo` label (`gh label create`)
6. Check access: GSC property reachable with service account? DataForSEO MCP responds? → report what's missing
7. Register product on dashboard
8. Open one PR containing everything; PR body lists the owner's remaining manual steps

### `brand` — extract branding from the repo
Trigger: called by `init`; owner re-runs after a brand change. Reads the repo only; no rendering, no images.
1. Extract: `tailwind.config.js` / CSS vars → palette; layout Blade files → fonts, radius; `public/` → logo; name/domain from config
2. Write `brand.json` (contract in §5) with `derived_from` and `defaults_used`; check WCAG contrast, set `on_primary`
3. Write a `## Design system` block into `CLAUDE.md` between markers (the Claude Code design skill reads it)

### `frames` — build the frame kit
Trigger: called by `init` after `brand`; owner re-runs to refresh, or with `--from-canvas <url>` after approving a Claude Design canvas.
1. Copy default templates (`_base.css`, six frames) into `/seo/frames/`; never overwrite owner-edited files
2. Write `DESIGN-BRIEF.md` (a ready `/design` prompt)
3. State-driven re-runs: draft canvas → owner edits → convert artboards into tokenised frames → contact sheet
4. Render `contact-sheet.png`; check fonts, contrast, logo, slots; attach to PR

### `analysis` — Monday
Two modes. **Seeded mode** is v1 and always runs; **discovery mode** is added once GSC is wired.

**Seeded mode** — keywords → content briefs. For each tracked keyword in `strategy.md` without a backlog item:
1. DataForSEO SERP: top 10 URLs, PAA questions, featured snippet type, AI overview presence, volume, difficulty
2. Fetch the top 5–10 pages; extract H2 outline, questions answered, format (guide/listicle/table/tool), publish/update dates
3. Intent classification: informational / comparison / how-to / tool
4. Gap: what none of the top results cover well, where they are outdated, what angle the product uniquely has
5. Our coverage: existing article targeting it or adjacent → `refresh` instead of `write`
6. Write a backlog item with an attached **brief** (contract below). `write` refuses to run without one.

Brief contract (inside the backlog item):
```
- brief:
  intent: <type>, <who is searching>
  must cover: <3–6 topics the SERP expects>
  must answer: <PAA questions verbatim>
  angle: <what top results miss or get wrong; the product's unique take>
  format: <guide|listicle|comparison>, <word range>
  images: <suggested types from §15 catalogue>
  internal links: <existing articles, hub>
  avoid: <generic intros, topics covered elsewhere, never-write list>
  sources: <URLs read>
```

**Discovery mode** (later) — reads GSC (28d vs prior 28d via `gsc.js`), DataForSEO competitor ranked keywords, GEO monitor, `done.md`, `rejected.md`, open PRs.
Finds:
- **striking distance**: queries pos 8–20, impressions ≥100/28d → refresh
- **decaying**: pages with impressions −30% vs prior period → refresh or consolidate
- **gaps**: tracked/competitor keywords with no page of ours in top 50 → write
- **links**: pages that should link to each other and don't → link
- **technical**: from last crawl → fix
Scores each 1–10: potential × ease × fit (fit from `strategy.md`; never-write list = fit 0, item dropped).
Writes: `backlog.md` (rewritten, existing claimed/in-review items preserved), `data/gsc/<date>.json`, `data/ranks/<date>.json`. Commits to main directly (planning files only).
Posts: 10-line summary.
Caps: respects weekly caps in `strategy.md` when ordering; may propose tracked-keyword additions as a separate PR.

### `refresh` — Tue–Thu
1. Exit if open SEO PRs ≥ `open_prs_max`
2. Take top `open` backlog item of type `refresh`; mark `claimed`
3. Branch `seo/<id>-<slug>`
4. Pull `serp_context` for the target keyword; read the article; read `voice.md`
5. Edit: add/expand sections the SERP rewards, update dates/figures, FAQ, internal links, meta; regenerate OG via `images` if title changed
6. `validate-article.js`
7. PR with template body (§8); label `seo`; mark backlog `in-review:<pr#>`

### `write` — Tue–Thu
Same shell as `refresh`, for type `write`:
- outline from cluster context in `strategy.md` + sibling articles (hub-and-spoke)
- draft per `voice.md` and `templates/article.md`
- image plan from the brief: one entry per image with `type` (§15 catalogue), `section`, `data`, `alt`; hero always; 3–5 total; then `images`
- internal links to hub + siblings; meta + schema
- word count within range; no claim about the product that can't be verified against the live UI/docs

### `images` — called by `refresh`/`write`
Input: the image plan (list of `{id, type, data…, alt}`), types `hero stat compare steps quote` only.
For each entry: `render.js --frame <type>` with the entry as data. Read each PNG; check legibility, clipping, logo, font; shorten text and re-render once on failure, else drop the image. Output to the article's image folder. No AI, no browser — every image is a frame filled with the article's own content.

### `review` — after `refresh`/`write`, fresh session
1. Find open SEO PRs with no `ready`/`needs-work` label
2. Check out branch; read article, PR body, `review-rubric.md` + default rubric, `rejected.md`
3. Checks: target keyword/intent match; voice compliance; never-write list; word range; every product claim verified against the repo's docs/feature list; every image came from `/seo/frames/` and its numbers/steps/quotes appear in the article text, alt text matches content; links resolve; frontmatter valid; nothing lifted from a competitor page; would any past rejection reason apply?
4. Fail → PR comment with specific fixes, label `needs-work`; the next execution run revises. Max 2 rounds, then label `escalate`.
5. Pass → label `ready`, first comment = 5-line verdict. If PR type ∈ `strategy.md` auto-merge list → `gh pr merge --squash --auto`.

### `feedback` — 1st of month
- For each `done.md` item merged ≥4 weeks ago with no outcome: pull GSC for that page, record position/clicks delta
- `gh pr list --state closed --label seo` → close reasons into `rejected.md`
- Recurring themes (≥3) → propose `voice.md` / `review-rubric.md` lines via PR
- Dashboard: outcomes + rejection tally

### `audit` — quarterly or on demand
Crawl site → `data/crawl/<date>.json`: broken links, missing/duplicate meta, orphan pages, thin pages, redirect chains, sitemap gaps, CWV from PageSpeed if reachable. Trivial fixes → one PR. Rest → `backlog.md` as `fix` items.

## 8. PR template

```
## Why
<evidence line from backlog: keyword, position, impressions, CTR>

## What changed
- ≤5 bullets

## Preview
<OG image and illustrations used, inline>
<preview URL if CLAUDE.md defines one>

## Checks
validate: pass | links: n/n | words: n | review: pending
```

Owner reviews on GitHub mobile: read bullets, glance at images, open the preview URL if one exists, merge or close-with-comment. Never edits by hand; if 80% there, merge or close with the fix as a comment.

## 9. Guardrails (hard-coded in skills, not left to judgement)

- Max 1 PR per run; max `open_prs_max` open SEO PRs (default 3) — exit if full
- Never touch articles with human commits in last 14 days
- Never delete; consolidation = redirect + explanation
- Never-write list enforced at scoring (item never enters backlog)
- Word count floor/ceiling from `strategy.md`
- No publishing without PR; auto-merge only via `strategy.md` list and only after `ready`
- Never auto-merge if: review failed twice, article touches pricing/compliance claims, or `strategy.md` changed this week
- Idempotent: re-run same day → no-op

## 11. Dashboard

One claude.ai Dashboard artifact, private, pinned. Agent-written rows via `dashboard.js`, tagged by product. Panels:
1. Queue — open SEO PRs, status, link, justification
2. Backlog — top 10 scored, claimed state
3. Rankings — tracked keywords now vs 4 weeks ago; striking-distance count; decaying pages
4. Outcomes — merged items + 4-week result; rejection reason tally
5. Last run per skill per product

Not a control panel. Merge/close happens on GitHub.

## 14. Non-goals (deliberately out)

- Link building / outreach
- Programmatic SEO pages
- Social distribution
- Any publish path that bypasses a PR
- Custom agent console / run logs UI
- Hosting anything: no `seo-ops` app, no DB
- Browser automation of any kind: no product screenshots, no demo accounts, no Playwright against live sites
- AI image generation of any kind; every image is a filled frame template

## 15. Images & branding

**Decision**: no AI-generated imagery. Every article image is a brand-driven HTML frame filled with content from the article itself, rendered locally to PNG/WebP. Deterministic, free, always on-brand, and the images carry information (numbers, steps, comparisons) rather than decoration.

### Frame kit (generated by `frames` into `/seo/frames/`)

| Frame | Size | Slots | Typical use |
|---|---|---|---|
| `hero` | 1200×630 | eyebrow, title, description | OG + article header |
| `stat` | 1600×900 | number, label, source | a limit, a price, a percentage |
| `compare` | 1600×900 | 2–3 columns, rows | plans, tools, before/after |
| `steps` | 1600×900 | 3–5 numbered steps | how-to sections |
| `quote` | 1600×900 | sentence, attribution | key takeaway |

All frames: brand palette, heading/body fonts, radius, logo mark bottom-left, motif as subtle background. Templates read `brand.json` at render time via `render.js` tokens. Owner may hand-edit any frame; `frames` won't overwrite an edited one except when converting an approved Claude Design canvas.

### Authoring the frames
Default templates ship with the plugin. Optionally `frames` drafts a Claude Design canvas from `DESIGN-BRIEF.md`; the owner edits artboards; `frames` converts them back into tokenised templates and re-renders the contact sheet. State lives in `seo/frames/canvas.json`.

### Planning images (`write`/`refresh`)
3–5 per article, chosen from the article's structure: number → `stat`, table → `compare`, ordered how-to → `steps`, key sentence → `quote`, `hero` always. No structure → hero + quote. Never manufacture a stat to fill a slot.

### Checks (`images` after render; `review` on the PR)
Text legible, nothing clipped, logo visible, font loaded; every number/step/quote on a frame appears in the article; alt text describes the content.
